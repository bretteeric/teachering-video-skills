# 功能操作與分鏡

要求是「**操作所有功能進行功能說明**」。所以先有完整清單，再逐項決定怎麼示範，最後用程式驗證沒有漏。

---

## 一、覆蓋原則

`inventory.py` 的 `features.json` 是清單的起點，**不是終點**：

| 來源 | 意義 | 要做的事 |
|---|---|---|
| `nav+live` | 選單上有、也實際打開過 | 一定要示範 |
| `live` | 爬到但不在選單（登入頁、明細頁） | 通常要示範，它們是流程的一環 |
| `nav` | 選單有但爬不到（被導向登入、出錯） | 登入後示範；出錯就是專案問題，記下來回報 |
| `code` | 原始碼有、選單與爬蟲都沒走到 | 逐一判斷：POST 動作併進表單的操作示範；純樣板頁排除 |
| API 控制器 | 不在畫面上操作 | 用 mermaid 時序圖講，或在 screen 場景示範呼叫它的那個按鈕 |

每一項最後都要落在兩個地方之一：

- storyboard 某個 screen 場景的 `"feature": "fXX"`（一個場景涵蓋多項時用 `"features": [...]`）
- storyboard 頂層 `exclusions`，**附具體理由**

```json
"exclusions": [
  { "feature": "f08", "reason": "Lockout 頁需要連續輸錯密碼五次才會出現，以圖解說明鎖定機制" },
  { "feature": "f05", "reason": "Privacy 是範本預設頁，與本單元教學目標無關" }
]
```

`qa.py` 會檢查這件事，沒落地的功能會被列出來。

## 二、功能操作規劃表

寫分鏡之前，先在 `notes.md` 為每項功能填一列。**每一格都要實際走過確認**，不是讀程式碼猜的：

| 欄位 | 內容 | 例 |
|---|---|---|
| 進入 | 從哪裡點進來 | 側邊選單「授權驗證」 |
| 示範資料 | 要輸入什麼 | 無（頁面一打開就由瀏覽器實際打三個端點） |
| 操作 | 按什麼、依序 | 未登入看一次 → 登入管理者後再看一次 |
| 預期結果 | 畫面上會出現什麼 | 未登入：200／401／302 導登入頁，三列「符合預期」 |
| 技術重點 | 背後做了什麼、為什麼這樣設計 | API 回 401、頁面回 302 導登入——同一個 Cookie 驗證兩種失敗行為 |
| 坑 | 常見錯誤 | API 也被導向登入頁，前端拿到 HTML 解析失敗 |
| 圖解 | 要不要 mermaid、哪一種 | sequenceDiagram：瀏覽器／MVC／API 三條線 |

示範資料用**看得出是示範**的值（`demo@example.com`、`測試文件 v1`），不用真實個資。
會改變資料的操作（上傳、刪除、改版）要想好**順序**：先建立、再查詢、最後刪除，讓後面的畫面有東西可看。

## 三、場景模式

### 單一功能

```
[diagram 概念／流程]  ← 需要時才放：講「看不見的東西」
screen 進入頁面，框住主要區塊          1～2 句：這頁是做什麼的
screen 框住輸入欄位，輸入示範資料       1～2 句：要填什麼、為什麼
screen 框住按鈕                        1 句：按下去
screen 框住結果                        1～2 句：看到什麼、代表什麼
[slide 重點與坑]      ← 技術重點多時收斂成 ≤4 條
```

### 全片骨架

```
title    專案名稱＋一句話說明它解決什麼問題
diagram  整體架構（分層、元件、外部相依）
（功能 1 … 功能 N，依使用者實際操作順序，不是依選單順序）
slide    總結：這個專案學到的 3～4 個重點
```

**順序依操作動線**：先登入才能管理、先上傳才有文件可查。選單順序常常不是合理的教學順序。

### 硬規則

- **一個 screen 場景 = 一個標示框 = 1～2 句旁白 = 小於 15 秒。**
  screen 不加運鏡；而且 `compose.py` 會把場景長度平均分給場景內的影格，
  一個場景塞多個重點，標示框就會跟旁白錯開一格。
- 圖解與重點卡單場景 < 40 秒，太長就拆成兩張圖逐步揭露。
- 每個 screen step 預設都會截一張圖。不要的中間畫面加 `"shot": false`。

## 四、操作步驟寫法（`capture.py` 動作）

```json
{
  "id": "s07", "type": "screen", "feature": "f03",
  "steps": [
    { "action": "goto",  "url": "http://localhost:5310/Access", "shot": false },
    { "action": "wait",  "selector": "table tbody tr:nth-child(3)", "shot": false },
    { "action": "focus", "selector": "table tbody tr:nth-child(2)" }
  ],
  "narration": ["第二列是沒登入去打管理 API，你看，它回的是 401。"]
}
```

| 需求 | 寫法 |
|---|---|
| 框住某區塊但不點（指出結果、說明區） | `{"action":"focus","selector":"..."}`——截一張帶框影格後移除框 |
| 框住按鈕並點下去 | `{"action":"click","selector":"...","highlight":true}`——先截帶框影格，再點、再截結果 |
| 等非同步結果 | `{"action":"wait","selector":"<結果元素>"}`，**不要**用固定毫秒硬等 |
| 下拉選單 | `{"action":"select","selector":"#kb","value":"ltc"}` |
| 打字 | `{"action":"type","selector":"#q","text":"長照申請資格"}`（逐字 60ms） |
| 原始 JSON 回應 | `goto`（`"shot": false`）→ `zoom` 2 |
| 長頁面下方 | `{"action":"scroll","selector":"#result"}` |

| 上傳檔案 | `{"action":"upload","selector":"#file","path":"<絕對路徑>"}`（作業系統的檔案對話框截不到，直接交給 input） |

### 實測踩過的坑

- **`button[type=submit]` 會點到頂列的「登出」。** ASP.NET Identity 的登出是一個 POST 表單按鈕，
  在 DOM 裡排在頁面表單前面。一律把送出鈕限定在表單內，例如 `form[enctype] button[type=submit]`、
  `main form button`。症狀：送出後跑回首頁、後續後臺頁面全被導去登入。
- **會自動重整的頁面，一次性提示會消失。** 例如處理狀態頁每 2 秒重整，TempData 的「上傳成功」「已上傳過」
  橫幅只活到下一次重整。要框它，就在**同一個場景**裡點完立刻 `focus`（`click` 的 `wait` 設 600 左右、`shot: false`），
  不要留到下一個場景。
- **有狀態的示範要從乾淨狀態開始錄。** 記憶體儲存、上傳、改版這類操作做過一次就回不去；
  彩排或擷取失敗要重來，先 `launch.py stop` 再 `start`，狀態才會歸零。
- **身分會改變頁面內容。** 授權驗證這類頁面的「預期」是寫給匿名使用者的，登入後會整列變紅。
  匿名才看得對的頁面排在登入之前錄，登入動作本身（例如開發用登入網址）當成一個場景示範。

### 先彩排，再寫旁白

分鏡前先用一支小腳本把整條操作流程實際跑一遍，把每頁 `main` 的文字存下來（`rehearsal.json`）。
旁白裡的每一個數字、狀態、版本號都要能在彩排紀錄裡找到——例如「重用 2、重算 1」「命中 4 → 去重後 4」。
彩排常會揭露示範資料本身的問題：示範 PDF 太短，整份被切成一個片段，改版就永遠是「重用 0」，
驗收的增量改版項目過不了。這種事要在錄影前發現，不是在成品裡。

選擇器優先序：`#id` > `[name=]` > 穩定的 class > `inventory` 產生的 `nth-of-type` 路徑（最脆弱，頁面一改就壞）。
寫完先 `capture.py --scene sXX --headed` 單跑該場景確認，再全跑。

## 五、mermaid 選圖

| 要講的東西 | 圖種 | 例 |
|---|---|---|
| 分層架構、元件關係 | `flowchart LR` | Controller → Service → Repository → DB |
| 一次請求的來回 | `sequenceDiagram` | 瀏覽器 → MVC → API → 外部服務 |
| 授權／分流判斷 | `flowchart TD` 加菱形 | 已登入？是管理者？→ 200／302／403 |
| 資料表關係 | `erDiagram` | 文件 1─* 片段 |
| 狀態變化 | `stateDiagram-v2` | Pending → Processing → Done／Failed |

- 單張圖 ≤ 12 個節點；節點文字精簡，長說明交給旁白。
- 圖必須和**程式碼實際行為**一致——畫之前回去看 Service 真的怎麼走。
- 樣式由 `diagram.py` 自動套用（深色、紅棕框線、JhengHei 28px）。

## 六、操作旁白

在 create-video-skill `narration-style.md` 的所有規則之上，操作錄影再加四條：

1. **先說要做什麼，再做。** 「我們先來看授權驗證這一頁。」然後畫面才切過去。
2. **按下去之前講原因，按下去之後講結果。**
   「這邊按重新檢查。」→「你看，三列都是符合預期。」
3. **結果要解讀，不是複述。** 不要說「畫面顯示 401」，要說「API 這條回的是 401，
   代表它沒有把你導去登入頁，而是直接告訴前端你沒權限——這才是 API 該有的行為。」
4. **每個功能收尾一句「為什麼」或「坑」**，讓觀眾帶走的是觀念，不只是按鈕位置。

節奏上，一個功能大約 4～8 個場景、40～90 秒。整支影片功能多時可以到 10～15 分鐘，
但**不要為了湊長度重複講同一件事**。

範例（授權驗證）：

> 接下來看授權驗證這一頁，這頁是這個單元的重點。
> 它一打開，瀏覽器就會真的去打三個端點，表格裡的結果不是寫死的。
> 第一列是公開的 ping，誰都能打，所以回 200。
> 第二列是沒登入去打管理 API，你看，它回的是 401。
> 第三列是沒登入去開管理頁，這次回的是 302，把你導去登入頁。
> 同樣是沒權限，為什麼結果不一樣？因為 API 的呼叫端是程式，不是人。
> 程式拿到一整頁登入畫面的 HTML 是解析不了的，所以 API 一定要回狀態碼。
> 這個分流很多人會漏掉，前端就會一直莫名其妙地壞掉。
